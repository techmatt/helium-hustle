# Rules history

One row per `RULES_REVISION`, newest first: what changed in play and why.

| Revision | Item | What changed | Why |
|---|---|---|---|
| 8 | 035_program_loadouts_and_rate | Program loadouts: a career library (`Career.library`, at most `library_slots` 12, names up to `loadout_name_max` 40; new programs params) with `save_loadout`, `load_loadout`, `rename_loadout`, `delete_loadout`; a load skips the run's unlock and reveal refusals (such lines fail or read nothing). `rate` is production less demand: the day's change in stock before the clamp, less demand left unmet (`today.unmet`: what a building, command or project wanted of an input it ran short of, less what it got), so it stays negative through a brownout; it now counts program purchases, pad loading, boredom growth and Dream, which 031 left out. The view's `per_day` is that quantity for the next day (`change_per_day`, `overflow`, `unmet` beside it; `net_per_day` gone). An edit of a loaded program refuses only lines new to it. Bumped from `RULES_REVISION` 7. | Rulings (Matt, 2026-11-20): automation survives retirement, and a condition can see a shortage; one rate for the panel and the condition. |
| 7 | 031_program_conditions_and_build | A program line is an instruction (`state::Op`), not only a command: `build <building>` (optionally `up to N`), `buy land`, `if <condition>` with a single-indented body (no nesting, no `else`) and `wait until <condition>`. Conditions (`<reading> <cmp> <number>`, one optional `and`/`or`) are free; a processor's step passes false blocks and done `up to` lines, at most one loop of the program, then idles. Readings: amount, percent of cap, last-day rate (new `Run.day_net`), building count, day, pads ready, demand once revealed. The unlock is the career flag `program_logic`, set the first day `logic_unlock_processors` (new programs param, 2) processors work. Line JSON gains an `op` tag; scenarios' programs hold commands only. Bumped from `RULES_REVISION` 6. | Rulings (Matt, 2026-11-19): a player can automate construction from a program; the first step of a program language that keeps growing. |
| 6 | 030_bug_hunt | Unpaid upkeep withholds a building's effects: a type run at `frac` in the partial pass leaves `active − floor(active × frac)` copies unpaid (new `Holding.unpaid`), and grants (processors), stores, Launch Pads' pads and Arbitrage Engines' decay come from the working copies, from the next day; processors unpaid stay assigned and only `min(assigned, working)` run, the shortfall off the last programs first (assignments are bounded by the active Data Centers). A partial-pass type that ran in full is no longer marked `input_starved`. Bumped from `RULES_REVISION` 5. | Rulings (Matt, 030's two questions): a Data Center, Launch Pad or Arbitrage Engine short of energy read "running at 0%" yet worked in full, and programs-first (rev 5) makes them the usual ones short. |
| 5 | 029_energy_priority_breakdown | Programs are paid before buildings: the day runs upkeep-free buildings (Solar Panels), then programs, then the buildings that take upkeep on what is left (full passes, then partial). Overclocks count from that same day's pass (`until_day = day + days`, still `days` passes). Display-only state, which plays no differently: every flow recorded by source for the day, who ran short and of what, and a rolling average over `flow_average_days` (new economy param, 20). Scenarios gain required `panels` and `programs` keys; `late_unlocks` added. Bumped from `RULES_REVISION` 4. | Ruling (Matt): programs first, so Load Launch Pads keeps running while a building runs partial; a plain move of programs before the whole building pass would pay them only from yesterday's leftovers, which a partial day leaves at 0, so the split (his answer to the item's question). The breakdown makes shortages visible. |
| 4 | 027_art_in_game | `set_pad_good` on a loaded pad no longer fails: the cargo returns to its good's stockpile, up to the cap; the excess is lost and a `cargo_lost` Recent Activity line says how much. Two building descriptions drop "Nationalist-aligned." (the card's ideology chip says it; content hash only). Bumped from `RULES_REVISION` 3. | A parked edit (Matt): switching cargo should just work, not demand an unload the player has no button for. Saves from revision 3 are discarded (no migration, as asked). |
| 3 | 006_playable_ui | Boredom `base_cap` 500 → 1000 (+100 per Recreation Dome unchanged): a run with no command boredom now reaches the cap on day 1670, not 1170. Display-only state, which plays no differently: a run activity feed (`activity_kept` newest lines), each program line's outcome today, the last finished run's summary, and the cheat mark; cheat actions (grant, set boredom, jump ahead) for the debug menu. Bumped from `RULES_REVISION` 2. | The cap Matt played in the Godot build (a parked edit). The display state is what the playable UI shows (Recent Activity, line colors, the run summary); it moves the fingerprint, so it rides this bump. |
| 2 | 004_rules_revision1 | The Godot build's Arc 1 replaces `placeholder`: 12 modules (economy with multi-pass building resolution, boredom, flat Dream, programs and commands, shipments, demand with speculators and rivals, research, ideology, projects, events and the quest chain, achievements, career and retirement), content converted from `reference/data`, boredom cap 500 + 100 per Recreation Dome, exact whole powers (`Fx::pow_int`) for cost curves and per-rank factors. The golden game is now the scripted policy. Bumped from `RULES_REVISION` 1. | Revision 1 of the game: the playtested Arc 1 rules, as data and handoffs last specified them ([rules/](rules/README.md), conflicts in each page's *Port notes*). |
| 1 | 002_engine_scaffold | First engine: the `placeholder` module (credits, energy with a cap, Solar Panel bought with credits, daily sunlight draw). | A stand-in to exercise config, content, `Fx`, RNG, replay and native = wasm; the rules port replaces it. |
